## 2. Saga API

The source of truth is still **`proto/kahoots/broker/v1/broker.proto` in the `message-broker` repo**. Lab 5 adds two RPCs to `service Broker` and the saga messages; `Envelope`, `Reply`, `Event` and `service Endpoint` are unchanged, so a service that does not start sagas needs no new stubs. The copy below must stay identical to the repo.

| RPC | Implemented by | Called by |
|---|---|---|
| `Broker.StartSaga(SagaRequest) → SagaState` | the broker | the initiator (crafting-service, base-service) |
| `Broker.GetSaga(SagaRef) → SagaState` | the broker | the initiator, tests |

```proto
syntax = "proto3";
package kahoots.broker.v1;

// One request/response, Gateway->Service or Service->Service.
message Envelope {
  string request_id      = 1; // X-Request-Id, passed on everywhere
  string source_service  = 2; // "gateway", "exam-service", ...
  string source_instance = 3;
  string target_service  = 4; // queue name = service name, e.g. "world-service"
  string method          = 5; // GET, POST, PUT, PATCH, DELETE
  string path            = 6; // path inside the service, e.g. "/rooms/r1?x=1"
  map<string, string> headers = 7; // X-User-Id, X-User-Role, Idempotency-Key, ...
  bytes body             = 8; // JSON, UTF-8
  int32 timeout_ms       = 9;
}
message Reply {
  int32 status       = 1; // HTTP status code
  map<string, string> headers = 2;
  bytes body         = 3;
  string instance_id = 4; // the instance that answered
}
// One fire-and-forget event on a topic.
message Event {
  string event_id        = 1; // UUID, handlers are idempotent on it
  string topic           = 2; // e.g. "exam.passed"
  string source_service  = 3;
  string source_instance = 4;
  string request_id      = 5;
  bytes payload          = 6; // JSON, UTF-8
  string occurred_at     = 7; // ISO 8601 UTC
}
message PublishAck { string event_id = 1; repeated string subscribers = 2; }
message DeliveryAck { bool ok = 1; string error = 2; }

// ---- Lab 5: orchestrated sagas (the coordinator lives in the broker) ----

// One step of a saga: a Broker.Call the coordinator runs for the initiator.
message SagaStep {
  string name           = 1; // "resource.consume", unique inside the saga
  string target_service = 2; // "resource-service"
  string method         = 3; // POST, PUT, PATCH, DELETE
  string path           = 4; // path inside the service, e.g. "/resources/consume"
  bytes body            = 5; // JSON, UTF-8
  StepCall compensation = 6; // unset = step without compensation
}
// The call that undoes a step (same target_service as the step).
message StepCall {
  string method = 1;
  string path   = 2; // e.g. "/resources/consume/{actionId}/revert", ids filled in by the initiator
  bytes body    = 3;
}
message SagaRequest {
  string saga_id   = 1; // UUID generated by the initiator, the idempotency key of the whole saga
  string saga_type = 2; // "craft", "base-upgrade"
  string initiator = 3; // service that starts the saga, e.g. "crafting-service"
  repeated SagaStep steps = 4; // run in this order
  map<string, string> headers = 5; // X-Request-Id, X-User-Id, X-User-Role, copied to every step
  bool wait        = 6; // true = answer when the saga ends, false = answer at once with RUNNING
}
message SagaRef { string saga_id = 1; }
message StepState {
  string name    = 1;
  string status  = 2; // PENDING, RUNNING, SUCCEEDED, FAILED, COMPENSATING, COMPENSATED, SKIPPED
  int32 attempts = 3; // calls made for the step (compensation attempts included)
  string error   = 4;
  int32 http_status = 5; // last status code the step answered with
}
message SagaState {
  string saga_id   = 1;
  string status    = 2; // RUNNING, COMPLETED, COMPENSATING, COMPENSATED, FAILED
  repeated StepState steps = 3;
  bytes result     = 4; // body of the last successful step (COMPLETED only)
  string error     = 5; // why the saga did not complete
  string saga_type = 6;
  string initiator = 7;
  string created_at = 8; // ISO 8601 UTC
  string updated_at = 9; // ISO 8601 UTC
}

// Implemented by the Message Broker (message-broker:50051).
service Broker {
  rpc Call(Envelope) returns (Reply);
  rpc Publish(Event) returns (PublishAck);
  rpc StartSaga(SagaRequest) returns (SagaState); // Lab 5
  rpc GetSaga(SagaRef) returns (SagaState);       // Lab 5
}
// Implemented by EVERY service (its own GRPC_PORT, default 50051).
service Endpoint {
  rpc Handle(Envelope) returns (Reply);
  rpc Deliver(Event) returns (DeliveryAck);
}
```

gRPC status codes:
- `StartSaga` with no steps, an empty `saga_id`, or a step without `target_service` / `method` / `path` → `INVALID_ARGUMENT`.
- `StartSaga` with a `saga_id` that already exists → `OK` with the **existing** state; no second saga is started (whatever the new request contains).
- `GetSaga` for an unknown id → `NOT_FOUND`.
- `wait = true` and the caller's gRPC deadline runs out first → `DEADLINE_EXCEEDED` for the caller only; the saga goes on, read it with `GetSaga` or wait for the event (§5).

The Node client (`clients/node`) gets `startSaga(req)` and `getSaga(sagaId)` (Mihai).

## 3. The coordinator (inside the broker)

The saga is **orchestrated**: the broker runs the steps one by one, stores every transition in SQLite, and if a step fails it runs the compensations of the successful steps in **reverse order**.

| Rule | Detail |
|---|---|
| Durable state | Tables `sagas` and `saga_steps` in the broker's SQLite (`BROKER_DB_PATH`). Each transition is written **before** the next call is made |
| Transport | Each step and each compensation goes the same way as `Broker.Call`: least-load, circuit breaker, HA reroute (Lab 4 §9) |
| Headers on every call | the saga `headers` + `Idempotency-Key`, `X-Saga-Id`, `X-Saga-Step` |
| `Idempotency-Key` | step: **`{sagaId}:{step}`** · compensation: **`{sagaId}:{step}:compensate`** (`step` = `SagaStep.name`) |
| Step succeeds | `2xx` → step `SUCCEEDED`, the next step starts |
| Business failure | `4xx` → **no retry**, saga `COMPENSATING` |
| Technical failure | no instance, `UNAVAILABLE`, timeout, `5xx` → reroute as in Lab 4 (the key makes it safe); still failing → saga `COMPENSATING` |
| Compensation | successful steps, reverse order; a step without `compensation` is `SKIPPED`. All done → saga **`COMPENSATED`** |
| Compensation fails | retried after 1, 2, 4, 8, 16 s; after `MAX_DELIVERY_ATTEMPTS` (5) it goes to the DLQ with kind **`"saga-compensation"`** and the saga stays **`FAILED`** |
| Compensation impossible | the service answers `409` with the reason → no retry, straight to the DLQ, saga `FAILED` |
| Timeout | `SAGA_TIMEOUT_MS` (default `60000`) from `StartSaga`; exceeded → compensation, error `"saga timeout"` |
| Restart | when the broker starts, every saga in `RUNNING` / `COMPENSATING` is resumed from the stored step (the keys make the replayed call safe) |
| Concurrency | runs in the existing Thread-per-Request pool or a separate worker; **one worker per saga** at a time |
| `result` | the body of the last successful step, on `COMPLETED` |

Saga status: `RUNNING` → `COMPLETED`, or `RUNNING` → `COMPENSATING` → `COMPENSATED` / `FAILED`.
Step status: `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `COMPENSATING`, `COMPENSATED`, `SKIPPED`.

## 4. Every service in a saga

For a service, a saga is only two things: **an idempotent step and its idempotent compensation**.

| Rule | Detail |
|---|---|
| Step idempotency | Same `Idempotency-Key` twice → the same answer, no double effect |
| Compensation idempotency | Same `…:compensate` key twice → `200`, no effect the second time |
| Compensating something that never arrived | `200` with no effect, **never `404`** (the step may never have reached the service) |
| Business failure in a step | `4xx` with the usual error body → the coordinator compensates, does not retry |
| Technical failure in a step | `5xx` / timeout → reroute, then compensation |
| Compensation impossible | `409` with the reason → saga `FAILED`, compensation in the DLQ |

Ids used in compensation paths (`actionId`, `grantId`, `upgradeId`) are **generated by the initiator** before `StartSaga`, so every path is known when the saga starts.

### Saga catalog

| Saga | Initiator | Steps, in order | Compensations |
|---|---|---|---|
| `craft` | crafting-service | 1. Resource `POST /resources/consume` · 2. Player `POST /players/{playerId}/inventory` | 1. `POST /resources/consume/{actionId}/revert` · 2. `POST /players/{playerId}/inventory/grants/{grantId}/revert` |
| `base-upgrade` | base-service | 1. Resource `POST /resources/consume` · 2. Base `POST /bases/{id}/upgrades/{upgradeId}/apply` | 1. `POST /resources/consume/{actionId}/revert` · 2. – (last step) |

Step bodies are the Lab 4 bodies of those routes. If step 2 fails, the coordinator undoes step 1. The initiator keeps its own record (`craft PENDING`) and moves it to done / failed when the saga ends (§5); on `COMPLETED` Crafting still publishes `item.crafted`, Base `base.upgraded`.

### New internal routes

Only the broker calls them; the gateway answers `404` to users (Lab 4 §12).

| Service | Method | Path | Called by |
|---|---|---|---|
| resource-service | POST | `/resources/consume/{actionId}/revert` | broker (compensation of `craft` and `base-upgrade`) |
| player-service | POST | `/players/{playerId}/inventory/grants/{grantId}/revert` | broker (compensation of `craft`) |
| base-service | POST | `/bases/{id}/upgrades/{upgradeId}/apply` | broker (step 2 of `base-upgrade`) |

## 5. New topics

Added to the Lab 4 catalog (Lab 4 §4).

| Topic | Publisher | Subscribers | Payload |
|---|---|---|---|
| `saga.completed` | message-broker | the initiator (crafting-service, base-service) | `{sagaId, sagaType, initiator, result}` |
| `saga.compensated` | message-broker | the initiator (crafting-service, base-service) | `{sagaId, sagaType, initiator, error}` |

Both services subscribe to both topics and **filter on `initiator`**. A saga that ends `FAILED` is published on `saga.compensated` too, with the error; the payload carries `status` so the initiator can tell them apart.

## 7. Cache

| What | Value |
|---|---|
| Where | the gateway, **3 Valkey nodes**, a consistent-hashing ring in the gateway |
| Keys | `resp:v{ver}:{service}:{path}?{query}[:u{userId}]`, `ver:{service}`, `auth:tok:{sha256}`, `auth:user:{userId}`, `auth:revoked:{jti}` |
| Header | `X-Cache: HIT \| MISS \| BYPASS` on every `GET` answer |
| Invalidation | every successful write through the gateway on `/{prefix}/...` → `INCR ver:{prefix}-service` |
| Needed from services | nothing, except Player: `jti` in the JWT and the logout route |

## 9. ETL and Data Warehouse

Each owner writes `etl-service/src/extract/<service>.ts`:

```ts
export const source = "resource-service";
export async function extract(since: Date): Promise<Batch[]> { ... }
// Batch = { table: "fact_resource_op", key: ["source_id"], rows: Record<string, unknown>[] }
```

- Read **only from a replica** (`<db>:5433`, or Mongo `secondaryPreferred`), only rows with `updated_at` / `created_at` > `since`.
- Never write to the source. Never delete from the DW.
- Every row has `source_id` (the key in the source) and `updated_at`.
- Alexandru: Game sessions (duration, players, result), Exam attempts (course, score, pass/fail, time).
